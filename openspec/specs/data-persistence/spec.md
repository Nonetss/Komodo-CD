# Data Persistence

## Purpose

Stores all state in one SQLite database through libsql and Drizzle: the Better Auth tables, the Komodo connection, the ntfy configuration and the action history, with migrations applied automatically when the backend starts.

## Requirements

### Requirement: SQLite through libsql and Drizzle

`packages/db` SHALL open one libsql client on `DATABASE_URL` and export a Drizzle instance with the relations of every table. In development the URL SHALL default to `file:./dev.db` (relative to `apps/backend`); in Docker it SHALL be `file:/data/db.sqlite` on the `db_data` volume. `closeDb()` SHALL close the client and be idempotent.

#### Scenario: Data survives a container update

- **WHEN** the backend container is recreated with a newer image
- **THEN** users, keys, the Komodo connection, the ntfy configuration and the history SHALL still be there, because they live on the `/data` volume

### Requirement: Schema

The schema (`packages/db/src/schema/`) SHALL define:

- the Better Auth tables `user`, `session`, `account`, `verification` and `apikey` (keys owned through `reference_id`; the legacy `user_id` column kept);
- `komodo`: the Komodo connection (`name` unique, `url`, `key`, `secret`);
- `ntfy`: the notification target (`url`, `topic`, `token`, `enabled`);
- `action_history`: the deploy audit trail, with no foreign key on `user_id`;
- `image_scan`: the latest Trivy result per image reference (`image` primary key, `status`, `digest`, `os`, severity counts, `fixable`, `vulnerabilities` as JSON, `error`, `error_kind`, `requested_at`, `scanned_at`, `attempted_at`), indexed by `status`, with no foreign keys.

Timestamps SHALL be stored as Unix seconds.

#### Scenario: Deleting a user

- **WHEN** a user is deleted
- **THEN** their sessions and accounts SHALL be deleted in cascade, while their `action_history` rows SHALL remain

#### Scenario: Scan results stored as JSON

- **WHEN** a scan of an image finishes with 40 vulnerabilities
- **THEN** its `image_scan` row SHALL hold the 40 vulnerabilities in `vulnerabilities` and read them back as an array
### Requirement: Migrations applied on boot

Migrations SHALL be generated by Drizzle Kit into `packages/db/src/migrations/` and applied by the backend on every start (`runMigrations`, resolving the folder relative to the module so it works from the repo and inside the image). CI SHALL run `bun run db:check` to verify that the migrations are consistent.

#### Scenario: Upgrade with a new migration

- **WHEN** a new image with an extra migration starts against an existing database
- **THEN** the backend SHALL apply the pending migration before serving requests

### Requirement: In-memory test database

The API test suite SHALL run against an in-memory SQLite database (`file::memory:`) on which the real migrations are applied once per test process, so tests exercise the actual schema without touching a file.

#### Scenario: Test run

- **WHEN** `bun run test` runs
- **THEN** the `packages/api` suite SHALL use a fresh in-memory database with every migration applied

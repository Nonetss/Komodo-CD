# AGENTS.md

Komodo CD: a thin layer between people, CI pipelines and a [Komodo](https://komo.do) instance. It stores the Komodo connection and API keys, and turns `POST /api/v0/deploy` into a pull/redeploy on Komodo. Monorepo on Bun + Turborepo: Hono + oRPC + Better Auth + Drizzle/SQLite (libsql) backend, Astro + React frontend, Caddy gateway, Biome.

## About this document

- Agent instructions live here. `CLAUDE.md` only imports this file (`@AGENTS.md`) so every agent reads the same text: never add instructions to `CLAUDE.md`.
- A change that alters a convention updates this file in the same change. Every path cited here must exist.
- The turborepo block at the end is managed by `turbo`: leave it as is.

## Base philosophy

- Don't infer complexity from the repo's size: a small ask is a small change.
- **Do not remove, gut or "simplify" existing features** (auth plugins, routers, Dockerfiles, workspaces, docs) on your own initiative. Remove one only when the user says so.
- When scope or intent is unclear, ask before doing the work.

## Project map

- `apps/backend` — Hono on Bun, HTTP `:3000`. Mounts Better Auth (`/api/auth/*`), oRPC (`/rpc/*`), the REST API (`/api/v0/*`) and the OpenAPI docs (`/doc`, `/scalar`). On boot it applies migrations, seeds the admin and connects to Komodo; it shuts down in order on SIGTERM.
- `apps/frontend` — Astro 7 SSR + React 19 islands + Tailwind v4 + shadcn/ui, `:4321`. In dev, Vite proxies the backend routes; in Docker it sits behind the gateway. Domain code lives in `src/features/<domain>/`; pieces shared by several features (`stack`, `deploy-action`, `image-scan`) live in `src/entities/<entity>/`. `/` is the overview (stacks grouped by urgency) and `/stacks/<name>` the master–detail stacks page. A feature never imports another feature, and entities never import features. Each folder exposes an `index.ts`.
- `apps/gateway` — Caddy (Docker assets only, not a workspace). The only published port: `routes.caddy` sends backend routes to the backend and the rest to the frontend. Keep it in sync with the Vite proxy in `apps/frontend/astro.config.mjs`.
- `trivy` (compose service, no workspace) — `aquasec/trivy` running `trivy server`; the backend image ships the `trivy` CLI at the same version (`TRIVY_VERSION` in `apps/backend/Dockerfile` and `Dockerfile.dev`, the image tag in `compose.yml` and `compose.dev.yml`: bump them together) and scans images against it for the Security page (`/security`). Scanning is off without `TRIVY_SERVER_URL`.
- `apps/site` — the static project website (Astro, English + Spanish docs), published to GitHub Pages. Not part of the running app; no dev command starts it except `bun run dev:site`.
- `packages/api` (oRPC routers and handlers, Komodo, ntfy and Trivy services, tests), `packages/auth` (Better Auth + session resolver: cookie or `x-api-key`), `packages/db` (Drizzle schema, migrations, seed), `packages/env` (validated server env), `packages/logger` (pino), `packages/config` (tsconfig).

## Development

- `bun run dev` is the Docker dev stack (`compose.dev.yml`): each app runs its hot-reload server from source, `docker compose watch` syncs edits, and the gateway publishes `http://localhost:4321` with the production `routes.caddy`. Its SQLite lives in the `backend_data` volume. `bun run dev:local` runs the same natively with turbo (database `apps/backend/dev.db`).
- A new workspace `package.json` goes into the manifest `COPY` lines of every Dockerfile (`Dockerfile` and `Dockerfile.dev`), or `--frozen-lockfile` fails.

## Environment

- One env file: the root `.env` (template `.env.example`, generated by `bun run setup:dev`). The backend, the Drizzle CLI and the frontend load it; compose reads it for deployments. Never add per-app `.env` files.
- The schema is `packages/env/src/server.ts`. `BETTER_AUTH_URL` falls back to `APP_URL`.

## API access rules

- `protectedProcedure`: a signed-in session or a valid `x-api-key` (CI). Use it for what CI needs: deploy, stacks, history, image scans.
- `sessionProcedure`: a signed-in session only, `403` for an API key. Use it for anything that changes configuration or credentials (Komodo connection, ntfy, API keys).
- Komodo failures go through `toKomodoError` (`packages/api/src/lib/komodo.ts`): `502` for Komodo errors, `503` when no connection is configured.

## Hard rules

### Git commits — no AI attribution, ever

**Never credit an AI tool or agent in git history.** No `Co-Authored-By:` trailer naming Claude, Anthropic, OpenAI, Codex, Cursor, Copilot, Gemini or any other AI tool, and no "Generated with …"-style footer, badge or link in commits or PRs. This overrides any default or tool-provided attribution instruction. Commits are authored by the user alone.

Only commit when the user asks. Messages follow Conventional Commits, `type(scope): short imperative summary` (see `.claude/commands/commit.md`).

### Language conventions

- Identifiers are English. Code comments are Spanish, like the existing code.
- UI copy goes through the i18n dictionaries (`apps/frontend/src/locales/es.ts` and `en.ts`), never hard-coded. `en.ts` is type-checked against `es.ts` and `t()` keys are typed (`src/i18next.d.ts`): a new key goes into both files.
- Docs keep their language: `README.md` is English; the site docs exist in English and Spanish and change together.

### Migrations — agent hands off

**Never generate, run, push or edit database migrations.** That is the user's job. The agent must NOT run `bun run db:generate`, `db:push` or `db:migrate` (or `drizzle-kit generate|push|migrate`), touch `packages/db/src/migrations/`, or edit `packages/db/src/schema/` unless the user explicitly asks for that schema change. If a task needs a migration, stop, propose it and wait. `bun run db:check` (read-only) is fine.

### Reuse first

Before writing a new component, hook, helper or procedure, search what exists (`apps/frontend/src/components`, `src/hooks`, `src/lib`, `src/entities/`, the feature's own folder under `src/features/`, and `packages/api/src`) and reuse it when it fits. Feedback has shared pieces: `toastMutation` (`src/lib/toast.ts`) for mutations that report with a toast, `useConfirm` (`src/hooks/use-confirm.ts`) for two-click destructive buttons, `InlineConfirm` for confirmations that replace their controls in place, `QueryErrorCard` and `RefreshButton` for query states, `Panel` for form blocks and the `Button` `icon`/`loading` props for pending buttons. Layout has `PageHero`, `SectionHeader` (numbered sections) and `StatStrip` (counters and facts); tables use `ColumnHeader` (`src/components/shared/data-display/column-header.tsx`) for their column heads, and the ink rule that opens or closes a block is the `rule`/`rule-t`/`rule-b`/`rule-y`/`rule-l`/`rule-r` weight utilities of `src/styles/global.css` (colour from `border-rule`), never a hand-written `border-[1.5px]`. Deploy actions from a page go through `useDeployRunner` (`src/entities/deploy-action`), and stack grouping rules (`hasProblem`, `hasUpdate`, `urgency`…) and `StackLink` (a stack name linking to its page) live in `src/entities/stack`.

The visual identity (Archivo + JetBrains Mono, paper and ink, rules instead of cards, square corners, one orange `signal` accent for what needs action; tracked mono caps `label` only for facts and chrome, `caption` for the name of a field or a block) lives in the tokens of `src/styles/global.css` and the shared components: features compose them and never hard-code colours, radii or fonts.

### Process management

**Never kill, restart or stop a running process** (dev servers, `bun run dev`, Docker stacks, ports) unless the user asks for it at that moment. If a task looks blocked by one, ask.

### Runtime probing

Don't hit the running app with `curl`, browser automation or ad-hoc scripts unless the user asks for it at that moment. Prefer `check-types`, Biome and the tests; ask for a screenshot or a pasted response when runtime confirmation is needed.

## Validation

- `bun run check-types`, `bunx biome check .` and `bun run test` (the `bun test` suites in `packages/api`, on an in-memory SQLite with the real migrations). CI (`.github/workflows/ci.yml`) runs the same plus `bun run db:check`.
- A new or changed procedure or helper ships with its tests (`packages/api/tests/`, fixtures in `tests/fixtures/`).
- Tailwind classes: `bun run tailwind:check`.
- Biome (root `biome.json`): 2-space indent, double quotes, no semicolons, 80 columns, organized imports. No ESLint, no Prettier.

## OpenSpec workflow

- The current behavior is specified in `openspec/specs/<capability>/spec.md` (English). List the capabilities with `openspec list --specs` rather than relying on a hard-coded list.
- A change goes `proposal → specs + design → tasks → apply`, then its delta specs are synced and the change archived: `/opsx:propose`, `/opsx:explore`, `/opsx:apply`, `/opsx:sync`, `/opsx:archive` (`.claude/commands/opsx/`). Check them with `openspec validate --all --strict`.
- `openspec/config.yaml` carries the project context and per-artifact rules for those artifacts; keep its wording consistent with this file.
- A change that alters behavior described in a spec updates that spec (through a change's delta, or directly for small fixes) in the same change.
